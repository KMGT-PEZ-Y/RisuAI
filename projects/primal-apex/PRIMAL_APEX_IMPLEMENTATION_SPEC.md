# Primal Apex 구현 명세

작성일: 2026-09-08  
상태: 초기 구현 기준  
대상: RisuAI Lua 모듈과 LLM 서사

이 문서는 2026-09-08에 새로 정리한 플레이 경험과 설계만을 기준으로 한다. 기존 `docs/specs/PRIMAL_APEX_IMPLEMENTATION_SPEC.md`의 구조와 요구사항을 계승하지 않는다. 기존 문서는 참고 이력으로 남기며, 이 문서가 새 프로토타입의 구현 기준이다.

## 1. 목표와 핵심 루프

Primal Apex는 두 가지 경험을 연결한다.

- 경기에서는 간단한 턴제 복싱 전투와 스킬 육성을 중심으로 단순한 전략 RPG를 즐긴다. 복잡한 전략 체계를 목표로 하지 않는다.
- 경기 사이에는 등장인물과 상호작용하며 이야기를 진행하고, 다음 상대와 싸울 이유를 만들고, 플레이어를 강화한다.

핵심 루프는 다음과 같다.

```text
복싱 경기
→ 경기 후 두 선수의 상호작용
→ NPC와의 서사 전개
→ 다음 대진 및 일정 확정
→ 자원을 사용한 훈련과 정비
→ 입장 장면
→ 다음 복싱 경기
→ 반복
```

경기 후 장면은 스토리모드의 일부다. 선택적 NSFW 장면을 포함할 수 있으며, 참여하지 않아도 다음 경기로 진행할 수 있다.

서사는 관계와 대전 계기를 남겨 다음 대진에 영향을 준다. 토너먼트나 미리 작성된 시나리오에서는 정해진 대진 흐름을 따른다. 다음 경기는 강화된 플레이어의 성능을 확인하고 쌓인 이야기를 전투로 풀어내는 자리다.

## 2. 설계 범위와 원칙

구현은 허브, 매치메이킹, 트레이닝, 경기, 스토리모드의 다섯 모듈을 중심으로 한다.

- 허브는 전체 패러미터를 보관하는 상태 집합과 버튼형 UI다.
- 각 모듈은 자기 기능의 선택지, 화면, 처리를 담당한다.
- 모듈 간 연결은 허브에 저장된 상태와 모듈의 반환 결과를 통해 이루어진다.
- 저장은 허브를 통해 수행한다. 모듈이 서로의 내부 함수를 직접 호출하지 않는다.
- 별도 범용 이벤트 버스, 세분화된 엔진 계층, 복잡한 변경 명령 체계는 만들지 않는다.
- 패러미터를 보기 좋게 보여주는 status panel은 후속 작업으로 미룬다.
- 기존 BattleSim의 전투 기능과 UI는 가능한 범위에서 재사용한다.

## 3. 확정한 기본 동작

| 항목 | 규칙 |
|---|---|
| 스토리 시간 | 진입 시 현재 시각을 전달하고, 대화 중에는 텍스트로만 흐름을 표현한다. 종료 패킷의 종료 시각을 검증한 뒤 실제 시간을 갱신한다. |
| 장면 길이 | 장면당 고정 시간이나 한 칸 소비 규칙을 두지 않는다. |
| 훈련 | 시간 없이 강화 자원만 소비한다. |
| 확정 대진 | 다음 경기가 이미 잡혀 있으면 재추첨하지 않는다. |
| LLM 결과 | 관계 변화, 보상, 대전 계기는 허용된 키워드로 반환한다. 임의 수치나 새 보상을 만들지 않는다. |
| 종료 시각 | 관계·보상 키워드와 구분되는 시각 필드로 받는다. |
| 시간 이동 | 허브의 캘린더 버튼으로 원하는 미래 시각을 선택한다. |
| 경기 시각 | 예정 시각에 도달하거나 경과하면 경기 시작만 실행 가능하다. |

이전에 논의한 필수 훈련 완료 여부는 첫 구현의 경기 시작 조건에 넣지 않는다. 강화할 자원이 없어도 일정에 맞춰 경기를 시작할 수 있다.

## 4. 허브와 저장 패러미터

### 4.1 역할

허브는 전체 스토리의 패러미터, 현재 스테이지, 진행도, 플레이어 성장, 경기 일정과 기록을 보관한다. 현재 조건에 따라 각 모듈의 가능 여부와 선택지를 표시한다.

스테이지와 화면은 구분한다. 스토리 화면을 열거나 닫았다는 이유만으로 전체 스테이지가 전진하지 않는다. 스테이지는 시나리오에서 정한 완료 조건에 따라 갱신한다.

### 4.2 초기 저장 형태

```lua
state = {
    version = 1,
    revision = 0,

    scenario = {
        id = "default",
        mode = "free", -- free / tournament
        stage = "opening",
    },

    calendar = {
        now = 0, -- 게임 시작 기준 누적 분
    },

    player = {
        name = "Player",
        stats = {},
        skills = {}, -- 스킬 ID와 레벨
        loadout = {},
        trainingPoints = 0,
    },

    story = {
        relationships = {}, -- NPC별 관계 값
        flags = {},
        matchLeads = {}, -- 도전, 재대결 제안, 약속 등
        recentSummaries = {},
    },

    schedule = {},
    matchHistory = {},

    session = nil, -- 진행 중인 story 또는 battle
}
```

NPC 기본 스펙, AI 설정, 스킬 정의, 장소와 시나리오 정의는 데이터 테이블로 보관한다. 저장 상태에는 내부 ID와 변경된 값을 중심으로 기록한다. 실제 경기 진입 시 사용할 참가자 설정은 복사해 고정한다.

버튼의 활성 여부와 후보 목록은 저장하지 않고 현재 상태에서 계산한다.

### 4.3 첫 허브 UI

| 버튼 | 표시와 동작 |
|---|---|
| 매치메이킹 | 상대 선정 또는 이미 확정된 일정 확인 |
| 트레이닝 | 강화 가능한 스킬, 비용, 보유 자원 표시 |
| 경기 | 시작 가능 여부와 이유 표시, 진행 중이면 이어 하기 |
| 스토리 | 지도, 장소, 인물, 가능한 상호작용 표시 |
| 시간 이동 | 원하는 날짜·시각 선택 또는 다음 경기까지 이동 |

각 버튼은 불가능한 경우 그 이유를 표시한다. 진행 중인 스토리나 경기가 있으면 새 세션을 만들지 않고 해당 세션을 이어간다.

## 5. 캘린더와 시간 처리

### 5.1 표현

Lua에는 누적 분을 저장하고 화면과 LLM 패킷에는 날짜와 시·분을 표시한다. 게임 내 날짜는 초기에는 1일차, 2일차 같은 형식을 사용한다.

예를 들어 1일차 00:00을 0으로 잡으면 2일차 09:00은 1,980분이다.

### 5.2 시간 변화

| 행동 | 시간 처리 |
|---|---|
| 허브, 지도, 설명 열기 | 변화 없음 |
| 스토리 대화 중 | 실제 값은 유지하고 텍스트로만 흐름 표현 |
| 스토리 종료 | 검증된 종료 시각으로 갱신 |
| 훈련, 장착 변경 | 변화 없음 |
| 매치메이킹 | 변화 없음 |
| 시간 이동 | 선택한 허용 시각으로 갱신 |
| 경기 완료 | 정해진 경기 소요 시간 반영 |

경기 소요 시간의 구체적인 값은 조정 항목이다. 실제 사용자의 대화 시간이나 버튼 클릭 간격을 게임 시간으로 사용하지 않는다.

### 5.3 스토리 종료 시각 검증

- 시작 시각보다 이전으로 돌아갈 수 없다.
- 확정된 다음 경기 시각을 넘길 수 없다.
- 다음 경기 시각은 스토리 요청에 장면 종료 상한으로 전달한다.
- 경기 시각에 도달한 것으로 서술했다면 장면을 마무리하고 경기 준비로 연결한다.
- 종료 패킷이 잘못되면 시간과 보상을 먼저 적용하지 않고 수정 요청을 제공한다.

### 5.4 시간 이동 버튼

- 다음 경기가 없으면 현재 이후의 원하는 시각으로 이동한다.
- 다음 경기가 있으면 해당 경기 시각까지 이동한다.
- 경기 이후 시각을 선택하면 경기 시각에서 멈추고 경기 시작을 활성화한다.
- 진행 중인 스토리나 경기에서는 허브 시간 이동을 사용할 수 없다.
- 과거 이동이나 일정 무시는 일반 플레이에 포함하지 않는다. 필요하면 개발용 편집 기능으로 별도 추가한다.

## 6. 경기 모듈

### 6.1 흐름

```text
허브의 경기 시작
→ 확정 경기와 참가자 설정 전달
→ 플레이어 최종 정비 UI
→ 정비 확정
→ LLM 입장 장면 묘사
→ 경기 개시 버튼
→ BattleSim 턴제 전투
→ 결과 확인
→ 허브로 결과 반환
```

최종 정비에서는 보유한 스킬의 장착 등을 조정한다. 캠페인 중 능력치나 미보유 스킬을 임의로 수정하는 기능은 일반 정비에 포함하지 않는다.

입장 묘사 전에 참가자 설정을 확정한다. 입장 장면의 종료를 자동 추정하지 않고 경기 개시 버튼으로 전투에 들어간다.

### 6.2 입력과 출력

| 방향 | 정보 |
|---|---|
| 입력 | 경기 ID, 상대 ID, 장소, 규칙 |
| 입력 | 플레이어 능력치, 보유 스킬, 장착 상태 |
| 입력 | 상대 능력치, 스킬, AI 방식과 정책 설정 |
| 입력 | 대전 이유, 관계, 관련 사건의 짧은 요약 |
| 출력 | 승자, 종료 방식, 라운드 수 |
| 출력 | 다운 횟수, 주요 스킬 등 서사에 필요한 경기 특징 |
| 출력 | 최종 장착 상태와 경기 후 장면용 확정 사실 |

진행 중 전투는 `session`에 보관해 이어갈 수 있게 한다. 완료 시 허브가 기록을 저장하고 일정을 완료 처리한다. 이어서 스토리모드의 경기 후 상호작용을 우선 제시한다.

## 7. 스토리모드

### 7.1 흐름

```text
스토리 버튼
→ 간단한 지도와 장소별 인물 표시
→ 장소, 인물, 상호작용 선택
→ Lua가 장면 요청 패킷 생성
→ LLM이 상황 또는 짧은 퀘스트 제시
→ 사용자의 자유로운 반응과 대화
→ 서사 마무리 또는 사용자 종료 명령
→ 요약과 종료 패킷 반환
→ Lua 검증 및 결과 적용
→ 허브 복귀
```

경기 후 두 선수의 장면과 다른 NPC를 만나는 장면은 모두 이 모듈이 담당한다. 첫 구현은 주요 상호작용 대상 한 명을 중심으로 장면을 구성한다.

### 7.2 장면 요청 정보

| 항목 | 내용 |
|---|---|
| 장면 | 장면 ID, 장소, 참가자, 상호작용 종류 |
| 시간 | 시작 시각, 다음 경기로 인한 종료 상한 |
| 문맥 | 현재 스테이지, 관련 관계·플래그, 최근 사건 요약 |
| 결과 범위 | 허용된 관계 변화, 보상, 대전 계기 키워드 |

LLM은 제공된 문맥과 결과 범위 안에서 퀘스트와 상황을 구성한다. 사용자는 자유롭게 반응할 수 있다. 대화 중 기계적 상태를 계속 바꾸지 않고 장면 종료 시 정산한다.

### 7.3 종료 패킷

다음은 초기 형식 예시다.

```text
<STORY_END|scene=s12|end_day=3|end_time=16:30|affinity=UP_SMALL|respect=NONE|reward=TRAINING_SMALL|lead=REMATCH_OFFER>
```

- `scene`으로 대상 NPC, 시작 시각, 허용 결과를 확인한다.
- `end_day`와 `end_time`은 종료 시각이다.
- 관계 값은 절대 수치 대신 `NONE`, `UP_SMALL`, `DOWN_SMALL` 같은 변화 키워드로 받는다.
- 보상은 `NONE`, `TRAINING_SMALL` 등 등록된 키워드로 받는다.
- 대전 계기는 제안과 확정 약속을 구분하는 등록된 키워드로 받는다.
- 키워드의 실제 수치와 효과는 Lua 데이터 테이블에서 결정한다.
- 관계 축은 초기에는 `affinity`, `respect` 정도로 시작하고 필요할 때 확장한다.

구체적인 키워드 목록과 수치 매핑은 콘텐츠 작성 시 확정한다. 모든 장면에 모든 키워드를 허용하지 않고 요청에 포함된 범위만 승인한다.

### 7.4 적용과 오류 처리

종료 시각, 관계 변화, 보상, 대전 계기를 모두 검증한 뒤 함께 저장한다. 실패하면 어느 항목도 먼저 적용하지 않는다.

장면 ID별 결과는 한 번만 적용한다. 완료 후 같은 패킷이 다시 도착해도 보상이나 관계 변화가 반복되지 않는다.

잘못된 패킷에는 정산 재요청 또는 보상 없이 종료하는 복귀 경로를 제공한다. 보상 없이 종료할 경우 실제 시간은 마지막으로 저장된 값에 유지한다.

서사 요약은 최근 문맥으로 저장한다. 매치메이킹이나 보상 계산은 요약문을 재해석하지 않고 검증된 관계 값, 플래그, 대전 계기를 사용한다.

선택적 NSFW 내용은 스토리모드 안에서 진입하거나 건너뛸 수 있다. 참여 여부가 필수 성장이나 다음 경기 진행을 막지 않는다.

## 8. 트레이닝 모듈

```text
훈련 진입
→ 현재 스킬, 강화 가능 여부, 비용 표시
→ 강화 선택
→ 자원 차감과 스킬 강화
→ 허브 복귀
```

| 입력 | 출력 |
|---|---|
| 보유 스킬과 레벨, 강화 자원, 강화 비용과 한도 | 갱신된 스킬, 남은 자원, 강화 결과 |

- 초기 자원은 `trainingPoints` 하나로 시작한다.
- 자원 차감과 강화는 함께 적용한다.
- 훈련은 시간을 소비하지 않는다.
- 자원 부족, 최대 레벨 도달 등은 선택지에 이유를 표시한다.
- 신규 스킬 획득은 같은 UI에 확장할 수 있으나, 첫 연결 구현은 기존 스킬 강화부터 시작한다.

## 9. 매치메이킹 모듈

### 9.1 자유 진행

```text
다음 예정 경기 유무 확인
→ 없으면 출전 가능한 후보 구성
→ 관계와 대전 계기로 가중치 조정
→ 상대 한 번 선정
→ 날짜와 장소 확정
→ 캘린더 저장
```

입력은 현재 스테이지, 관계, 대전 계기, 과거 경기 기록, 현재 시각이다. 출력은 확정된 상대와 일정이다.

단순한 후보 가중치 테이블로 시작한다. 도전 제안은 확률을 높이고, 직전 상대는 확률을 낮추는 식이다. 반드시 특정 상대와 싸우기로 한 약속은 추첨 가중치가 아니라 지정 대전 조건으로 취급한다.

이미 예정 경기가 있으면 기존 일정을 표시한다. 허브 복귀, UI 갱신, 버튼 재입력으로 재추첨하지 않는다.

### 9.2 일정 형태

```lua
{
    id = "match_03",
    opponentId = "npc_b",
    at = 6720, -- 누적 분, 예: 5일차 16:00
    venueId = "local_arena",
    reason = "REMATCH_PROMISE",
    status = "scheduled", -- scheduled / completed
}
```

### 9.3 토너먼트

토너먼트 모드는 정해진 일정을 캘린더에 미리 등록한다. 탈락식 대회는 날짜와 대진 구조를 고정하고, 선행 경기의 승패로 결정되는 상대는 결과 확정 후 채운다. 상대까지 정해진 각본형 시나리오는 전체 상대를 미리 지정할 수 있다.

허브, 트레이닝, 경기 모듈은 자유 진행과 같은 일정 형식을 사용한다.

## 10. 버튼 활성 조건

| 상황 | 매치메이킹 | 트레이닝 | 경기 | 스토리 | 시간 이동 |
|---|---|---|---|---|---|
| 다음 경기 없음 | 선정 가능 | 자원과 스킬에 따라 가능 | 불가 | 가능한 장소·인물 표시 | 미래 시각 선택 |
| 경기 예정, 시간 남음 | 기존 일정 확인 | 자원과 스킬에 따라 가능 | 아직 시작 불가 | 가능한 장면 표시 | 경기 시각까지 가능 |
| 경기 시각 도달·경과 | 실행 불가 | 불가 | 시작 가능 | 불가 | 실행 불가 |
| 경기 진행 중 | 불가 | 불가 | 이어 하기 | 불가 | 불가 |
| 스토리 진행 중 | 불가 | 불가 | 불가 | 이어 하기·종료 | 불가 |
| 경기 후 장면 대기 | 장면 정리 후 가능 | 자원과 스킬에 따라 가능 | 다음 일정 조건에 따름 | 경기 후 장면 우선 표시 | 장면 정리 후 가능 |

경기 후 장면은 짧게 마무리하거나 건너뛸 수 있다. 이미 잡힌 다음 경기 시각에 도달했다면 경기 시각 제한이 우선하며 선택적인 경기 후 장면이 출전을 막지 않는다.

## 11. 모듈 인터페이스와 저장

다섯 파일 중심으로 개발한다.

```text
projects/primal-apex/
  PRIMAL_APEX_IMPLEMENTATION_SPEC.md
  src/
    hub.lua
    matchmaking.lua
    training.lua
    battle.lua
    story.lua
```

NPC, 장소, 스킬 효과, 시나리오 등은 필요할 때 작은 데이터 파일로 분리한다. 별도 관리 엔진은 추가하지 않는다. `battle.lua`는 기존 BattleSim을 연결하는 역할부터 시작한다.

각 기능 모듈은 다음 형태를 사용한다.

```lua
Module.options(state)                  -- 가능 여부, 선택지, 비활성 이유
Module.enter(state, selection)         -- 화면 또는 세션 시작
Module.handle(state, action, payload)  -- 버튼 또는 패킷 처리
```

반환값은 다음처럼 단순하게 유지한다.

```lua
{
    ok = true,
    state = updatedState,
    done = false, -- true이면 허브로 복귀
    message = nil,
}
```

허브는 상태 복사본을 전달하고 성공한 결과만 저장한다. 모듈은 담당 영역을 갱신하며, 허브는 경기 기록과 스테이지 등 공통 진행 정리를 담당한다. 화면을 열거나 표시하는 것만으로 보상, 추첨, 시간 경과가 발생하지 않게 한다.

최소 안정성 규칙은 다음과 같다.

- 버튼 실행 시 현재 상태로 가능 여부와 입력을 다시 검증한다.
- 성공한 변경만 한 번에 저장한다.
- 저장 변경 시 revision을 증가시키고, 이전 revision의 버튼은 거부한다.
- 스토리 장면 정산과 경기 완료 처리는 각각 한 번만 적용한다.
- 진행 중인 세션을 저장해 재진입 시 이어간다.

## 12. 첫 구현 순서와 완료 기준

### 12.1 구현 순서

1. 허브 상태 저장, 다섯 버튼, 시간 이동과 경기 시각 제한을 구현한다.
2. 소수 NPC의 대진 확정과 기존 스킬 강화 기능을 연결한다.
3. 확정 정보를 BattleSim에 전달하고 경기 결과를 허브로 회수한다.
4. 작은 지도, NPC 선택, 스토리 시작 문맥과 종료 패킷을 연결한다.
5. 경기 후 서사부터 다음 경기까지 한 사이클을 반복 검증한다.

### 12.2 연결 플레이 완료 기준

```text
경기 완료
→ 경기 후 상호작용
→ NPC 서사에서 대전 계기와 강화 자원 획득
→ 종료 시각 반영
→ 다음 상대와 일정 확정
→ 자원을 사용해 스킬 강화
→ 경기 시각까지 이동
→ 정비와 입장 장면
→ 강화된 플레이어로 다음 경기
```

- 다음 상대가 정해진 서사적 이유를 확인할 수 있다.
- 훈련의 변화가 실제 전투 설정에 반영된다.
- 자유 대화의 길이와 관계없이 종료 패킷으로 게임 시간이 갱신된다.
- 예정 경기 시각에는 스토리와 훈련을 시작할 수 없다.
- 확정 대진은 재추첨되지 않는다.
- 잘못된 패킷은 상태를 부분 변경하지 않는다.
- 중복 버튼과 중복 종료 패킷이 강화나 보상을 반복 적용하지 않는다.
- 선택적 서사 내용을 건너뛰어도 경기 루프를 계속할 수 있다.

## 13. 구현 중 조정할 항목

다음은 구조가 아니라 콘텐츠와 밸런스에 해당하므로 초기 연결 이후 조정한다.

- 관계 변화와 보상 키워드의 정확한 목록 및 수치 매핑
- 훈련 비용, 강화 한도, 신규 스킬 습득 조건
- NPC 후보 가중치와 경기 일정 간격
- 경기 완료 시 적용할 소요 시간
- 장소, 인물, 상호작용 종류와 시나리오별 접근 조건
- 최근 서사 요약의 보관 개수와 길이
- 상태 패널의 시각 디자인

이 문서에 없는 기존 명세의 기능은 자동으로 구현 범위에 포함하지 않는다. 실제 연결 플레이에서 필요성이 확인된 기능부터 추가한다.

# Python → RisuAI Lua 스킬 포팅 검토

검토일: 2026-09-05. 현재 로컬 소스와 배포 CHARX 기준. 이 문서는 비교·설계·에셋 명세이며, 전투 코드나 배포 모듈은 변경하지 않았다.

## 1. 결론과 확인 범위

Python의 액티브 스킬 실행기와 콘텐츠는 Lua로 이식할 수 있다. Lua는 무스킬 전투와 사진 연출을 갖추었으나, 스킬 실행 계층 전체와 선택 UI를 추가해야 한다. NG+ 탐색도 언어상 구현 가능하지만, RisuAI 안에서의 실행 시간과 취소·화면 갱신은 아직 검증하지 않았다.

- Python 기본 결과표 27행과 그로기 결과표 3행의 수치를 Lua 선언과 비교해 모두 일치함을 확인했다. 전체 전투 상태·AI 동작의 교차 언어 일치를 입증한 것은 아니다.
- `BattleSim.lua`: 729줄. 기존 구조 검사기 통과. 이 검사기는 괄호·블록 등을 점검하며 Lua 실행 테스트나 전투 규칙 검증을 대신하지 않는다.
- `BattleSim-RisuAI.charx`를 읽어서 내장 Lua·CSS가 현재 소스와 일치함을 확인했다.
- 해당 CHARX에는 아이콘 `assets/icon/image/main.png`만 있으며, 전투 사진 38종은 포함되지 않았다. 모듈의 assets 목록도 비어 있다. 실행 중인 RisuAI에 사용자가 별도로 주입한 에셋은 이번 검토 대상이 아니다.
- Python은 최근 149개 자동 테스트를 통과했고, NG+ 13개 덱 × 100경기 실험을 완료했다. Lua에는 대응하는 스킬 테스트가 아직 없다.

## 4. 필요한 구현

### 4.1 데이터와 저장

Python의 선언 데이터를 검증한 뒤 Lua table 또는 내장 JSON으로 자동 출력한다. ID·레벨·조건·효과·UI 설명을 두 언어에서 수작업으로 각각 관리하지 않는다. 미지원 연산은 조용히 무시하지 않고 빌드나 로딩에서 거부한다.

개발 소스는 데이터·전투·AI·UI로 나누고, 배포 시 하나의 Lua 트리거로 합치는 구성이 가능하다. 현재 CHARX 빌드도 단일 Lua 트리거와 별도 backgroundHTML CSS를 사용한다. 실행 시 로컬 Python 파일을 읽는 방식은 사용하지 않는다.

저장에는 장착 ID/레벨, CD, 잔여 횟수, 비용 보정, 상태/예약의 정의 ID·기간·부여 턴·소비 상태, 공개 행동/스킬 이력, RNG 상태, 선택 중인 입력과 전투 버전이 필요하다. 함수·코루틴·순환 참조·NG+ 탐색 분기 전체는 저장하지 않는다. 스킬 정의와 런타임 상태를 분리한다.

RisuAI의 setState는 JSON 직렬화를 사용한다. 현재 upstream 구현에는 Lua/Wasmoon, async·sleep·reloadDisplay가 있으며 실행은 mutex를 거친다. 따라서 Python Thread를 그대로 번역할 수 없고, 협력적 분할 실행 및 취소 이벤트 도달 가능성을 실제 앱에서 검증해야 한다. 저장소에 있는 RisuAI.exe의 파일 버전 정보는 0.0.0이어서 upstream 기능이 그 설치본에 모두 존재한다고 단정할 수 없다. [공식 Lua 문서](https://kwaroran.github.io/docs/srp/lua/), [공식 실행기 소스](https://github.com/kwaroran/RisuAI/blob/main/src/ts/process/scriptings.ts)

### 4.2 입력과 효과 실행

1. 합법 행동 집합과 스킬 사용 가능 사유를 계산한다.
2. Player와 Enemy의 기본 행동+스킬 의도를 각각 확정한다. Enemy에는 이번 Player 선택을 전달하지 않는다.
3. 양측 입력이 유효한 경우에만 비용·사용 횟수·CD를 확정한다. 오래된 버튼과 중복 클릭은 경기/턴 식별자로 거부한다.
4. 기존 timing 순서에 맞춰 비용 확정 → 행동 공개 → 원본 주사위 → 주사위 수정 → 결과표 수정 → 동시 반영 → 결과 후 효과 → 상태 부여 → 턴/인터벌 처리를 실행한다.
5. 자원 변경, 결과값 변경, 주사위 변경, 행동 제어, 상태 제어, 스킬 제어를 공통 실행기로 처리한다. 피해량·회복량을 스킬별 if문으로 별도 구현하지 않는다.
6. 기본 결과 변화가 없을 때 추가 피해를 만들지 않는 계약, 부호 있는 수치의 floor, HP 0 이후 회복 금지, 다운/KO 한 번 판정을 유지한다.

### 4.3 지속·예약·연계에서 반드시 보존할 규칙

- 다음 자기 턴 활성화, 행동하지 못해도 소모되는 기간, 정화 가능 여부, refresh/replace, 예약 trigger/expires/consumes.
- 현재 Lua의 인터벌 일괄 -2턴 처리는 그대로 재사용할 수 없다. 기존 C/D 상태와 M/U/H의 인터벌 차감 규칙을 각각 보존해야 한다.
- 피해 준비끼리·할인 준비끼리는 각각 한 개만 존재한다. 할인 최소 STA 8, U04 일반 스킬 CD 하한 2, 결정기 CD 감소 제외.
- H04→H05는 H05 비용을 할인하지 않고 할인 기간만 한 턴 연장. H06 사용 다음 턴 스킬 금지, H02 다음 턴 공격 금지.
- M07/U07/H07의 제거는 결과 후 발생하며 이미 소비된 준비 효과를 소급 취소하지 않는다.
- 최대 5슬롯, 제어 M09/U08/H08 중 최대 하나, 결정기 H06/H09/H10 중 최대 하나, H08+H09 동시 장착 금지.

### 4.4 AI

쉬움 적 3종의 일정형 선택은 현재 기본 행동을 먼저 결정하고 스킬을 덧붙이는 계약을 유지한다. NG+는 별도 선택기로 기본 행동과 스킬을 함께 결정한다. 12종 모두를 자동으로 NG+로 교체하지 않는다.

NG+는 공개 상태 복제, 합법 후보, 상대 모델, 실제 규칙을 쓰는 가상 실행, 평가, 3턴 탐색, 1턴 기대값 보정, softmax와 판단 충실도를 이식해야 한다. 일반 전투와 예측이 동일한 순수 전이 함수를 사용하고, 탐색 중 저장·화면 출력·실전 RNG 소비는 금지한다.

첫 목표는 Python 기본 D3/K4/B2/F4·가상 턴 상한 6,552와 의미를 맞추는 것이다. 상태 테이블 복제·정렬·이벤트 할당 비용을 줄이고 실기에서 측정한다. 느리다는 이유로 예고 없이 탐색 깊이나 판단 충실도를 바꾸지 않는다. 런타임 응답 시간 목표는 사용자 결정 사항이다.

Python은 random.Random, Lua는 현재 LCG라 같은 정수 시드가 같은 주사위열을 만들지 않는다. 먼저 동일한 행동·스킬·주사위열을 주입해 전투 결과를 맞춘다. 언어 간 AI 선택까지 재현하려면 RNG, 후보 정렬·동률 순서, 표본 난수 흐름, 수치 비교 규칙도 별도로 일치시켜야 한다.

### 4.5 UI와 연출

| 화면 | 추가 요소 | 기본 제안 |

| 경기 설정 | 캐릭터, 행동/스킬 AI, 13개 덱 프리셋, 양측 장착, 레벨, 시드, 판단 충실도 | 캐릭터 외형과 AI·덱을 분리 |
| 이번 턴 | 행동 선택, 스킬/미사용, 허용 행동, 현재 할인 비용·CD·횟수, 실행 버튼 | 선택만으로 턴을 실행하지 않고 별도 확정 |
| 스킬 설명 | 효과·조건·대상·후딜·연계, 사용 불가 이유 | 선택 시 바로 표시, 호버와 터치 상세 보기 모두 지원 |
| 상태 | 피해/할인 준비, 디버프·제어·후딜·예약, 발동/만료/정화 여부 | 효과 이름과 다음 턴 영향 표시 |

| AI 계산 | 입력 잠금, 계산 중 표시, 완료 후 결과, 취소/새 경기 처리 | 실제 런타임에서 가능한 취소 방식 검증 |
| 검사 | 단계별 결과, 판단 근거, 스킬 사용 통계, 테스트 시드 | 일반 화면에서 접을 수 있는 진단 패널 |

현재 공격/방어/회피 버튼은 즉시 playTurn을 호출한다. 행동+스킬을 선택한 뒤 실행하는 구조로 바꿔야 한다. HTML select 값이 자동으로 Lua에 전달된다고 가정하지 않고 현재 risu-btn 콜백과 setState로 선택 상태를 연결한다.

현재 presentation은 자원 변화와 기본 행동·주사위만 보관한다. 스킬 추가 후에는 한 턴 안에 피격과 회복, 반격, 준비 소비가 함께 발생하므로 최종 순변화만 보고 사진을 선택하면 사건이 사라진다. 타격 피해·회복·상태 전환을 구분한 이벤트 목록을 보관해야 한다. 인터벌을 화면에서 따로 보여주더라도 논리상 회복·기간 차감은 정확히 한 번만 수행한다.

기존 Lua 연출에는 `side=='player' and playerValue or enemyValue`를 false/nil이 가능한 값에 사용하는 곳이 있다. 예컨대 Player 무피격(false), Enemy heavy이면 Player도 heavy를 선택할 수 있다. actionPortraitPath, effectReactionPath, statusReactionPath 및 renderCharacter의 관련 분기를 명시적 양측 선택으로 고치는 것이 선행 수정 항목이다. 사용자 취향 결정이 필요한 사항은 아니다.

| 5 | NG+ 탐색과 계산 중 처리 | 가상 실행=실행 결과, 정보 비노출, RNG 보존, 실기 성능 확인 |
| 6 | CHARX 빌드·가져오기·저장/재시작·사진 회귀 | 배포 내용=소스, PC 실제 플레이 완료, 필요 시 모바일 확인 |

Python 테스트 개수를 기계적으로 Lua로 복사하지 않는다. 동일 입력·주사위의 기준 결과, 무효 입력 무소비, 상태·예약 경계, 양측 동시 효과, 그로기·다운·라운드 종료, 저장 복원, UI 이중 확정 방지를 중점 검증한다. 대규모 덱 매트릭스는 Python에 유지해도 된다.

## 7. 현재 사진 에셋 전체 목록

파일명의 `{name}`은 현재 구현에서 Player는 `player`, Enemy는 NPC 정책 ID다. 예: 처형자 상대는 `player_*` 38장 + `executor_*` 38장, 합계 **76장**이다. 같은 플레이어를 유지하고 적만 추가하면 적당 38장씩 늘어난다. 기존 NPC 12종을 전부 준비하면 Player 포함 **494장**이다.

현재 유효한 적 접두사:
`rookie_cycle`, `rookie_guard`, `reckless_raider`, `balanced_soldier`, `veteran_guard`, `cautious_hunter`, `pressure`, `adaptive`, `tactical_evaluator`, `weighted_analyst`, `regret_duelist`, `executor`.

NG+와 13개 덱은 아직 Lua 상대 목록에 없다. 현재 assetBase는 strategy를 이미지 접두사로 사용하므로 NG+를 바로 추가하면 `ng_plus_*`만 찾게 된다. 포팅 시 `characterAssetKey`, `actionAI`, `skillAI`, `deckId`를 분리하여 같은 인물 사진으로 여러 덱을 쓸 수 있게 한다.

## 8. 스킬 포팅 후 추가 사진의 선택 범위

스킬 실행에 필수인 추가 사진은 **0장**으로 설계할 수 있다. 기본 38종에 스킬 이름·효과 아이콘·수치·준비/후딜 표시를 더하면 모든 스킬을 우선 표현할 수 있다.

추가 연출을 원할 때만 아래 8개 공통 동작을 캐릭터당 제작하는 방안을 제안한다. **아직 코드가 읽는 이름이 아니며 확정 전 제작 필수 목록에 포함하지 않는다.** 모두 1:1, 1024×1024, 투명 PNG 제안이다.

| 제안 파일명 | 용도 |
|---|---|
| `{name}_skill_attack.png` | 강화 공격 |
| `{name}_skill_guard.png` | 가드·반격 준비 |
| `{name}_skill_heal.png` | 회복·재정비 |
| `{name}_skill_prepare.png` | 피해·할인 준비 |
| `{name}_skill_disrupt.png` | 준비 해제·자원 견제 |
| `{name}_skill_dice.png` | 집중·판정 보정 |
| `{name}_skill_control.png` | 도발·행동 제한 |
| `{name}_skill_finisher.png` | 결정기 |

공통 연출 8장을 채택하면 캐릭터당 46장, Player+특정 적 한 명은 92장이다. 스킬별 고유 사진이나 정사각형 아이콘은 이와 다른 선택이며 자동으로 30장/52장을 요구하지 않는다.

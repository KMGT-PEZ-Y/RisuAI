# LAST BELL 설계

## 목표

복싱에서 상대의 리듬을 읽고 빈틈을 만드는 경험을 짧은 결정 퍼즐로 만든다. RisuAI 채팅의 버튼 인터페이스에서, LLM의 출력이나 외부 서버 없이 재현 가능한 게임을 제공한다.

## 기존 battle-sim과의 차이

이 작업에서 기존 프로젝트를 참고한 부분은 **RisuAI 배포 형식, Lua 호스트 API, JSON 및 HTML 검증 방식**이다. BattleSim 엔진·스킬·정책·UI·캐릭터 사진은 재사용하지 않았다.

- 중심 단위는 행동 하나와 스킬의 조합이 아니라 **확정 예고에 응답하는 세 박자 계획**이다.
- 공격 성공을 주사위나 스탯 대결로 정하지 않는다. 이동, 거리, 방어의 상호작용으로 명중과 피해가 결정된다.
- 덱·장착·쿨다운을 두지 않았다. 동일한 13개 행동으로 모든 상황에 대응하고, 바로 다음 박자로 이어지는 잽·회피·페인트 연결을 쓴다.
- 거리 하나와 양쪽 로프 압박을 표시한다. 2D 좌표계를 주장하지 않는 단순한 링 운영 추상화다.
- 경기 준비용 대규모 설정 화면 대신 스타일 선택 → 라이벌 스카우팅 → 훈련 → 경기 → 코너 → 결과의 커리어 흐름을 사용한다.
- UI는 민트·코랄 색의 두 코너, CSS로 그린 링과 선수 실루엣, 3개 예고 카드와 3개 계획 칸으로 구성한다. 외부 이미지가 없어도 완전한 화면이 된다.

## 상태 전이

```text
HOME → GYM → FIGHT / PLAN → REPLAY
                 ↑             ├─ 다음 교환 → PLAN
                 │             ├─ 라운드 종료 → CORNER → PLAN
                 │             └─ 경기 종료 → RESULT
                 └──── 패배·무승부 / 승리 후 다음 상대
                                      └─ 다섯 번째 승리 → CHAMPION
```

플레이어가 버튼을 누를 때만 상태를 변경한다. 화면을 그리는 함수와 계획의 호흡 부족 예측은 저장 상태를 바꾸지 않는다. 모듈은 자체 DOM 스크립트 대신 호스트 `risu-btn`으로 이벤트를 받는다.

## 전투 해결

1. 박자 시작 호흡으로 양쪽 행동의 비용을 지불한다. 부족하면 호흡 행동으로 전환한다.
2. 시작 로프 압박을 기준으로 이동 가능 여부를 확인한다. 양쪽 거리 변화를 합산하고 압박 변화도 대칭적으로 적용한다.
3. 사거리 안의 클린치가 있다면 양쪽 타격을 취소하고 중앙에서 분리한다.
4. 같은 타격 전 상태에서 양쪽 피해를 계산한 후 동시에 적용한다. 이전 박자 연결, 방어, 스타일, 훈련, 로프 머리 피해 +1이 반영된다.
5. 체력 KO, 충격 다운, 누적 3다운 TKO를 판정한다. 동시 종료는 무승부이며 다운은 미실행 박자를 취소한다.
6. 기본 호흡 회복 및 호흡 행동의 추가 회복을 적용하고 박자 리플레이를 기록한다.
7. 네 번째 교환에서 공개 점수표를 기록한다. 마지막 라운드가 아니면 코너 선택 후 다음 라운드로 간다.

## 범위와 의도적 단순화

한 플레이어와 다섯 라이벌의 싱글 플레이 커리어다. 맞춤 사진·멀티플레이·온라인 리더보드·실제 복싱 규정 전체는 포함하지 않는다. 3박자 예고를 항상 보여 주어 어려움의 원인을 운이 아닌 선택에서 찾게 한다. 고급 플레이어에게는 비교적 쉽게 풀 수 있는 캠페인이며, 테스트의 탐색 플레이어가 전승하는 것은 해법이 존재하는지의 확인이지 사람 대상 난도 평가가 아니다.

## 호스트 계약 참고

- 모듈 포맷·배경 CSS: https://github.com/kwaroran/RisuAI/blob/main/src/ts/process/modules.ts
- Lua 버튼·표시·상태 API: https://github.com/kwaroran/RisuAI/blob/main/src/ts/process/scriptings.ts
- HTML 정화 및 클래스 접두사: 저장소 내 공식 parser 소스 캐시를 확인. CSS와 HTML은 처음부터 `x-risu-lb-` 접두사를 사용한다.

네트워크·LLM·낮은 수준 권한을 사용하는 API를 호출하지 않는다. `onStart`는 두 개의 정확한 명령어만 가로채고 일반 대화는 유지한다.
